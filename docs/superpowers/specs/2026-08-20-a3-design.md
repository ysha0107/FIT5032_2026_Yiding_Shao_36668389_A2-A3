## 2. Data & Auth Architecture

Firebase becomes the source of truth for shared data; localStorage becomes a cache/offline queue (still satisfies B.2 dynamic-data spirit, and powers F.1 offline innovation).

- **Firebase Auth** — email/password + Google popup. `stores/auth.js` rewritten:
  - `onAuthStateChanged` listener drives `currentUser` ref
  - profile doc (`name`, `role`, `email`, `createdAt`) in Firestore `users/{uid}`. First login upserts with `setDoc(..., {merge:true})` but **never overwrites an existing `role`** (default `client` only when the doc is created). Demo admin role is set by creating `users/{uid}` for admin@mindbridge.org with `role: 'admin'` in the Firestore console before first login.
  - `main.js` waits for first auth-state resolution before `app.mount()` so router guard stays synchronous
  - router guard unchanged in shape: `requiresAuth`, `roles: ['admin']`, `guestOnly`
  - demo accounts created in Firebase console (`week7-yidingshao` project): `admin@mindbridge.org` (admin), `sarah@example.com` (client) — same passwords as A2 (`Admin@123` / `Sarah@123`)
- **Firestore collections**
  - `users/{uid}` — profile + role (admin readable/writable; own doc readable)
  - `ratings/{itemId}_{uid}` — `{itemId, userId, score, createdAt, updatedAt?}` (authenticated users; read all, write own)
  - `contacts/{autoId}` — contact form submissions incl. attachment metadata (create: anyone, incl. unauthenticated — contact form is a public page; read: admin only)
  - `appointments/{autoId}` — `{date, time, serviceId, professionalId, userId, userName, status, createdAt}` (read all authenticated; create own; delete own or admin)
  - Security rules: `allow read: if request.auth != null` on ratings/appointments; contacts read only admin; own-write checks.
- **localStorage** (A3 role): `mindbridge_offline_queue` (contacts + ratings queued while offline, synced on `online` event), Firestore `enablePersistence()` for read cache. A2 keys (`mindbridge_users` etc.) retired once Firebase migration lands; ratings/contacts data is not migrated (fresh start acceptable — assignment demo data).
- **Static data stays static:** `resources.js` / `services.js` remain front-end datasets (B.2), mirrored by the Workers REST API for E.1/F.1.

## 4. BR-by-BR detail

### D.1 Firebase Auth
Register: client-side validations (B.1) → `createUserWithEmailAndPassword` → profile doc. Login: `signInWithEmailAndPassword` or `signInWithPopup(GoogleAuthProvider)` → upsert profile (role defaults `client`; admin role assigned via console for demo admin). Logout: `signOut()`. Router guard reads resolved `currentUser` (role from profile). Guard against Firestore profile fetch failure: block on auth-ready promise, show error state.

### D.2 EmailJS
Contact form gains attachment `<input type=file>` (size limit ~1 MB; metadata stored on Firestore contact). On submit → `emailjs.send(serviceId, templateId, {…, attachment})`. EmailJS v4 attachments supported via form file input. Bulk email (F.1#2): admin selects users (checkbox column in users DataTable) → composer (subject + body) → `emailjs.send` per selected recipient (or Bcc loop). Config via `.env` (`VITE_EMAILJS_*`); template built in EmailJS dashboard.

### D.3 DataTable
Props: `columns` ([{key,label,sortable}]), `rows`, `pageSize=10`, `rowKey`. Per-column text search inputs (one per column header cell), combined AND across columns; sort by clicking header (asc/desc/neutral, aria-sort attribute); pagination prev/next + "Page x of y" + count summary. All controls are native buttons/inputs with labels (E.3). CSV export button per table (filtered view).

### D.4 Cloudflare Pages
`npx wrangler pages deploy dist --project-name mindbridge` (direct upload — does not touch git). `public/_redirects` contains `/* /index.html 200`. Result: `https://mindbridge-*.pages.dev` public URL.

### E.1 Cloudflare Workers (`workers/mindbridge-api/`)
Single worker, ~4 routes (self-designed server-side logic):
1. `GET /api/resources` — JSON list of resources (mirror of front-end dataset), CORS `*`
2. `GET /api/resources/:id` — single resource
3. `POST /api/appointments` — receives booking payload; server-side validation (required fields, working hours 9–17 Mon–Fri, not past, conflict check against KV `appointments`), stores in KV, returns 201/409
4. `GET /api/appointments` — list from KV (admin debugging)
KV namespace bound in `wrangler.toml` (`mindbridge-kv`). Deployed with `wrangler deploy`. Routes 1–2 double as the F.1 "API access (2+ REST routes)" innovation.

### E.2 Leaflet map
`LocationsPage.vue`: full-height map; search box geocodes via Nominatim (`/search?format=json&q=`) and flies to result with marker; "services near" loads the 6 MindBridge service locations (seeded lat/lng in `services.js`); clicking a service marker → "Route here" uses OSRM (`router.project-osrm.org/route/v1/driving/{lon,lat};{lon,lat}?overview=full&steps=false`) to draw polyline + show distance/duration panel. Geolocation button (optional, browser prompt). Two non-trivial features = POI search/geocoding + routing.

### E.3 WCAG 2.1 AA (audit & fixes)
- Skip-to-content link as first focusable element on every page
- `:focus-visible` outline on all interactive elements (visible, 3px, high contrast)
- `aria-label` on icon-only buttons; `alt` on every informative image
- Form inputs: explicit `<label for>`, error text linked via `aria-describedby`, `aria-invalid`
- Dynamic messages (alerts, rating success, sync status) in `role=status`/`aria-live` containers
- StarRating: keyboard operable (tab to widget, arrow keys, `aria-label` per star, `role=radiogroup`/`slider` semantics)
- DataTable: `aria-sort` on headers, pagination is buttons with labels, search inputs labelled
- Contrast: fix amber `#f0a04b` text usage (use darker `#b06a1e` for text on white, AA ≥4.5:1); verify `#2c6f8f` on white (≈4.7:1) and button combinations; crisis banner `#c53030` on white ok
- Heading hierarchy audit (one h1 per page, no skipped levels)
- Final pass with https://www.accessibilitychecker.org on the deployed URL

### E.4 Export
- CSV: DataTable "Export CSV" (filtered rows, proper quoting, BOM for Excel)
- PDF: admin "Export report" via jsPDF — resources/services summary or appointment list; downloadable, opens in any reader

### F.1 Innovations (final 4)
1. **Appointment booking (FullCalendar)** — `AppointmentPage.vue`: week view, business hours 9–17, slot selection only on future weekdays; on submit client checks conflicts from Firestore `appointments` (same professional + overlapping time → blocked with message); server-side re-check via Workers `POST /api/appointments` (defense in depth); per-user limit 2 upcoming bookings. Admin sees all bookings in a DataTable (status management: confirm/cancel).
2. **Bulk email** — admin users table checkbox column → composer → EmailJS loop.
3. **Interactive charts (Chart.js, Firestore data)** — AdminDashboard: users-by-role doughnut, registrations per month bar, average rating per service bar, appointments per week line. Client Dashboard: own ratings history line (nice-to-have if time).
4. **Offline capabilities (2+)** — `network.js` store: `navigator.onLine` + `online/offline` events → OfflineBanner ("You are offline — new submissions will be queued"); contact submissions and ratings written to `mindbridge_offline_queue` in localStorage while offline and flushed to Firestore on reconnect (status toast via aria-live); Firestore `enablePersistence()` gives read cache offline.

## 5. Error Handling & Edge Cases

- Firebase blocked/offline → OfflineBanner + queue; auth pages show friendly error when Firebase unreachable
- EmailJS quota/failure → toast with error, contact still saved to Firestore (graceful degradation)
- Google sign-in popup blocked → fallback message to use email/password
- Nominatim/OSRM rate limits → user-facing "try again" message; map still shows seeded markers
- Workers conflict (409) → client re-fetches bookings and shows the conflicting slot
- Deleted/cancelled bookings excluded from conflict check and charts
